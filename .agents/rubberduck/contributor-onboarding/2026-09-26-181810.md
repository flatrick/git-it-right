# Rubber-duck: getting new contributors of a gir-enabled repo to actually use gir

### Idea (as floated)

Have `gir init` write a `.git-it-right.md` at the repo root explaining what gir is, why to use it, how to use it, why it adds `cliff.toml` (git-cliff), and how to use git-cliff.
Goal: new contributors to a gir-enabled project actually use gir.

Constraints added during the session:
- (turn 2) gir must serve both CI and non-CI setups; CI gets automation, non-CI still needs a working path.
- (turn 3, user decision) `gir init` SHALL write `GIT-IT-RIGHT.md` (visible name) when missing, same as `cliff.toml`.
  Maintainers remove what they don't want. git-cliff is a strongly suggested addition; gir must work without it.

### Holes, gaps & failure modes

1. **Now strongest: removal does not stick (verified in `src/cmd/init.rs`).**
   `write()` keeps a file only if it exists and differs; a missing file falls through and is re-written.
   So after a maintainer deletes `GIT-IT-RIGHT.md` or `cliff.toml` and commits the deletion,
   every contributor's `gir init` — the onboarding step itself — recreates them as untracked files,
   and a careless `git add -A` / `git commit -a` commits them back.
   "Maintainer's responsibility to remove" only holds if removal is durable. This already affects `cliff.toml` today.
2. **Without CI there is no enforcement on an un-activated contributor.**
   Git runs no repo code on clone (verified in README), so hooks and the "gir: not installed" warning are dormant until `gir init`.
   Non-CI levers are only discoverability and a merger-side check.
3. **Discoverability is improved but not solved.**
   Visible `GIT-IT-RIGHT.md` shows in `ls`, Explorer, and forge file lists — resolves the hidden-dotfile objection.
   Contributors still primarily read `README.md` / `CONTRIBUTING.md`.
4. **Drift.** Template content freezes at the gir version that wrote it; `init` won't overwrite edits without `--force`. Same as `cliff.toml`; accepted by precedent.
5. **git-cliff audience.** Contributors don't run git-cliff; maintainers do. In `GIT-IT-RIGHT.md` it should be a short, clearly optional maintainer section, not part of the contributor quick-start.

Conceded: "tool-owned prose in someone else's repo" (earlier objection).
Evidence: `gir init` already writes the optional `cliff.toml` for the maintainer to keep or delete; `GIT-IT-RIGHT.md` follows that established contract.

### Improvements / stronger alternatives

**Make removal durable (needed for the user's contract to hold):**
1. Preferred — distinguish *bootstrap* from *activate*:
   if `.girconfig` is tracked in `HEAD`, the repo already adopted gir, so `gir init` only activates the clone (hook shims if needed, `core.hooksPath`) and never recreates optional files.
   Full write only on first adoption or with `--force`. Zero config; a committed deletion is respected automatically.
2. Alternative — an opt-out list in `.girconfig` naming optional files `init` should skip. Explicit, but the maintainer must remember it; deletion alone does nothing.

**Discoverability (lever A, works everywhere):**
- `GIT-IT-RIGHT.md`: short — what gir is, install, `gir init`, `gir explain` — links upstream rather than copying docs; optional maintainer section for git-cliff.
- `gir init` prints one optional line for the maintainer to paste into `README.md` / `CONTRIBUTING.md` / `AGENTS.md` pointing to it.

**Merger-side backstop (lever B, non-CI):**
- Documented `gir lint --range main..<their-branch>` before merging.
- Possible `pre-merge-commit` hook — unverified, from memory: exists since ~git 2.24, doesn't fire on fast-forward, rebase, or forge web-UI merges; partial at best.
- Squash-merge policy: maintainer writes the only message that lands. Inferred: simplest non-CI guarantee.

**CI (lever C, automatic):** `gir lint --range origin/<base>..HEAD`; rejection message doubles as onboarding.

### Open questions

- In an already-adopted repo, should `init` restore missing *required* files (`.girconfig`, hook shims) while skipping *optional* ones (`cliff.toml`, `GIT-IT-RIGHT.md`)? Inferred: yes — gir can't function without the required ones.
- Non-CI contribution flow: forge web-UI merges vs local `git merge` / patches? Decides whether lever B can be a hook.
- Is fixing at merge (squash) acceptable, or must contributor commits themselves conform?

### Where it stands

Direction accepted by the user: `gir init` writes a visible `GIT-IT-RIGHT.md` when missing, alongside `cliff.toml`, both optional and maintainer-removable.
That contract is sound by precedent but currently broken in practice: deleted optional files are resurrected by every contributor's `gir init` (verified in `init.rs`).
Making removal durable — preferably by treating a tracked `.girconfig` as "already adopted, activate only" — is the precondition for the idea to work as intended.
Discoverability still benefits from a README/CONTRIBUTING link; non-CI enforcement still rests on a merger-side check.
